# Codex 开发指令：胡闹运动会网页联机版

## 一、目标与完成标准

请完成《胡闹运动会》Magical Athlete 的浏览器联机项目，包括联网研究、规则建模、美术设计、前后端实现、测试、GitHub 仓库和公网部署，持续执行到可以实际分享游玩的状态。

我的使用场景：我创建房间，把邀请链接发给同学；同学打开链接、输入昵称即可进入，同一房间支持 2～8 名真人玩家，人数包含房主。玩家无需注册、安装客户端、登录 GitHub 或成为仓库协作者。支持电脑浏览器和手机浏览器，默认简体中文。

保留原作的选秀、角色技能、掷骰移动、赛道效果、分场比赛和累计计分。“实时联机”指所有人同步看到同一局的操作、技能和结算，玩法按原作的回合制执行。

最终必须有：
1. 我账号下的 GitHub 仓库及完整源码。
2. 可以直接打开游玩的稳定 HTTPS 网站。
3. 游戏内可复制的专属房间邀请链接。
4. 从建房到终局、再来一局的完整流程。

首版范围集中在好友房完整对局、全部基础角色、美术和联机稳定性。

## 二、先精确研究游戏，再确定规则

研究对象锁定 CMYK 2025 版 Magical Athlete 基础盒。官方基础人数为 2～6 人，基础盒有 36 名角色；7～8 人使用单独标识的扩展模式。较早版本和 Second Wind 的内容须分别识别，避免混入本项目。

先使用英文关键词检索，优先阅读 CMYK 当前官方规则书、主创发布的修订、发行方 FAQ、完整卡面和实物赛道图。已有资料截至 2026-10-20；执行时还需检查是否有更新。

重点查阅 2026 年 8 月的规则更新。同一批角色同时抵达的处理等细节已发生修订，不能直接采用旧英文转录或中文速览。下方给出的 BGG 页面可能出现访问限制；如果无法取得全文，应使用发行方可访问资料交叉核对，如 IELLO 的官方 FAQ，并说明资料覆盖范围。

请建立 docs/rules.md 和结构化角色、赛道数据，记录：
- 规则版本、来源 URL、访问日期，以及实际核验到的页码或章节。
- 起始设置、选秀顺序、各轮选牌、暗选与揭示、行动顺序、四场赛程、赛道切换、各场奖分、结束条件和平局。
- 两人专用变体及一名玩家控制多个角色的处理。Player、Racer 和角色卡定义应分别建模。
- 双面赛道的格数、起终点、全部特殊格位置与效果；从官方规则和实物图核验后数据化。
- 每位角色的稳定 ID、英文原名、中文名、中文技能释义、触发时点、强制或可选、合法目标、作用范围、持续时间、特殊状态、来源和测试编号。
- 中文名需要统一；非官方译名明确标注为本项目译名。技能释义应准确，不杜撰背景设定或能力。

对资料冲突，优先检查最新 CMYK 明确修订，再核对当前规则书和发行方 FAQ 的版本。把事实、解释和网页扩展规则分开记录。只记录真正读到的来源和页码。

完整核验并实现基础盒 36 个角色。允许先用少量角色打通开发流程，但最终验收覆盖全部角色及必要组合。若某项关键信息仍无法确认，继续完成其余工作，并集中列出具体缺项、已查来源和影响；不得把猜测包装成官方规则。

## 三、2～8 人的模式设计

1. 标准模式：2～6 名玩家，分别遵守对应人数的官方规则；两人模式使用官方专用变体。
2. 扩展模式：7～8 名玩家，大厅和规则页显示“7～8 人扩展规则”。默认沿用每人四名角色、四场比赛、每场一名角色的框架；按人数扩展两次蛇形选秀，每次展示 2N 张候选牌，并保留原规则的起选位置变化。
3. 初始选牌保持唯一，8 人需要 32 张，不能通过复制同一张初始卡来凑数。还要核验 Egg、Twin、Copycat 等涉及额外抽牌或能力复制时的牌堆流程，不能仅凭初始卡数足够就认定扩展完成。
4. 优先保留原有角色能力和奖分体系。确实需要补充的牌堆不足、循环、超时等裁定写入 docs/house-rules.md，在相关界面可查看。未经验证不得声称扩展模式与官方模式具有相同平衡性。

## 四、必须完成的玩家流程

首页 → 创建房间或通过邀请加入 → 输入昵称 → 大厅选择模式与准备 → 选秀 → 每场暗选并统一揭示 → 赛前技能 → 轮流行动与技能响应 → 单场结算 → 下一场 → 总成绩 → 原房间再来一局。

具体要求：
- 大厅显示玩家、座位、房主、准备和连接状态，支持复制邀请链接及房间码。
- 只有满足人数且全员准备后才能开局。处理满员、房间失效、重复昵称和中途访问的情况；昵称相同不代表同一身份。
- 开局后锁定参赛席位，原玩家可以重连；新访客需得到明确提示。
- 有暗选环节时，其他玩家只能看到是否完成选择，统一揭示前看不到选择结果。
- 可选技能、目标选择、预测和重掷给对应玩家明确的操作入口；其他人的回合也可能需要响应。
- 比赛页能清楚看到当前行动者、自己的角色、骰子结果、位置、状态、累计分数和接下来需要谁操作。
- 显示简短中文事件日志，能解释是谁因什么技能移动、绊倒、传送或得分。
- 刷新和短时断线后恢复身份、角色、分数与当前待处理选择。房主离线后房间仍可继续，管理权可转交。
- 为长时间掉线和操作超时制定可配置且公开的房规；相关默认选择必须合法，不擅自把可选技能改成强制技能。

## 五、技术架构与规则引擎

优先采用 TypeScript + React/Vite + Node.js + Socket.IO，前后端同域部署到一个常驻服务。首版按单实例管理多个房间，使用持久化磁盘上的 SQLite 或部署环境现有的可靠数据库。

若已有授权环境明显更适合其他方案，可选择更合适的实现，例如 Cloudflare Durable Objects；先说明理由，只完成一条清楚、可维护的路线。选择框架和部署平台时查当前官方文档、兼容版本及限制。

规则引擎必须与页面渲染和网络层解耦：
- 服务器持有真实对局状态，统一生成随机结果，裁定合法动作、位移、技能、次序、胜负和分数。客户端提交操作意图并展示结果。
- 用明确的阶段状态机和可追溯的事件处理机制表达技能连锁。事件包含触发原因、来源角色、目标、前后状态、共同移动组等必要信息。
- 区分骰子面值、最终移动距离、主要移动、技能移动、传送、强制放置和同时移动。按照对应规则处理，不靠动画位置或碰撞来裁定。
- 结算先后由已核验规则决定，网络消息抵达速度不能决定技能优先级。需要玩家选择时，保存待处理选择并等待合法响应。
- 动画逐个播放不能改变规则上的同时性；播放速度也不能影响结果。
- 识别真正的无限循环和仍在推进局面的合法长连锁。保护服务的执行预算可以分批执行或暂停诊断，不得用任意技能次数上限截断合法结算。
- 骰子与其他随机结果由服务器生成并记录，支持用记录重放和用测试种子复现；未来随机信息不发给玩家。

联机可靠性要求：
- 玩家身份独立于昵称和 socket.id，使用不可猜测的重连凭据；邀请链接只授予加入能力，不携带任何玩家的身份凭据。
- 动作带 actionId、预期状态版本和确认结果；按房间串行处理，重发和重复点击只生效一次，过期或非法动作明确拒绝。
- 每位玩家只收到自己有权看到的数据，暗选内容在服务器分发阶段隔离。
- 支持重连后的事件补发或全量快照同步，不能只依赖 Socket.IO 内建连接恢复。
- 已确认动作对应的状态、待处理事件、分数、随机记录和去重信息可靠持久化，服务重启后可以恢复。确认成功与持久化的顺序必须一致。
- 输入校验、昵称安全渲染、房间容量、消息大小和请求频率有合理限制。密钥和身份凭据不提交到仓库、不出现在公开日志中。

## 六、美术风格与 skill

先看下方 CMYK 实物图、Angela Kirkwood 的插画项目和 Elizabeth Goodspeed 的设计说明，再确定 docs/art-direction.md。

视觉方向：鲜明原色、大色块、简单图形、带手绘感的轮廓、复古插画气质、夸张荒诞的角色表情和肢体比例。把赛道和角色作为画面中心，界面体现轻松混乱的桌游气氛。

交付要求：
- 36 个角色具有可区分的轮廓和能力视觉线索，统一线条、比例、色彩、阴影方式；角色卡、棋子和技能提示中的头像保持一致。
- 使用原创或明确允许复用的插画、字体与音效，记录来源和许可。原作者作品作为视觉参考，不直接假定可复制发布。网站清楚标识非官方项目。
- 先做统一的大厅、选人、比赛、结算样式，再完善全套资产。需要位图时优先使用当前可用的图像生成能力；其他情况下可制作原创 SVG 等可维护资产。
- 多人同格时采用清楚的堆叠或展开方式，8 人同场仍能辨认归属。玩家色、角色色与状态标识不要相互混淆。
- 中文正文和技能说明易读，手机端可点击展开详细规则，不依赖鼠标悬停。
- 动效用于解释掷骰、位移、绊倒、技能和奖励，提供静音与减少动效选项。

先检查当前已有的 skills、MCP 和 CLI，补充时从作者官方仓库核验现行 SKILL.md、适用范围、依赖、许可和版本。可优先考察：
- OpenAI game-ui-frontend：游戏界面、菜单、响应式布局和比赛区域的可读性。
- Anthropic frontend-design：从题材提炼色彩、字体和版式。
- Microsoft Playwright CLI/skills 或 Playwright MCP：浏览器联机验收、移动端检查和截图。
- GitHub 官方 MCP 或当前已授权的 GitHub CLI：仓库、提交及 Actions。

按本项目需要选用，记录实际使用的工具和来源。根据 Codex 当前支持的方式安装，避免套用其他产品的安装命令。检索结果中的旧路径须重新验证，不能虚构 skill 存在、已安装或已运行。对 3D、单机或其他场景的专用要求，按本项目的 2D 联机桌游范围判断是否适用。

## 七、GitHub 和部署

在我当前已授权的个人 GitHub 账号下创建新仓库，建议命名 magical-athlete-online，默认私有。名称冲突时选择新后缀，保留已有仓库内容。游戏邀请无需授予源码访问权限。

仓库应包含可维护的客户端、服务端、独立规则模块、角色与赛道数据、资产、必要测试、依赖锁文件、环境变量示例、Dockerfile、部署配置和 README。路径组织可以按实际框架调整。

GitHub Actions 至少运行类型检查、规则测试和生产构建。README 写清本地启动、生产部署、恢复状态、规则版本、扩展模式和更新方式。

部署时：
- 优先使用我已有且已授权的合适账号或服务器，选择低维护成本的方案。
- 核验 HTTPS/WSS、WebSocket、重启、休眠、持久化磁盘、数据库、额度和费用限制。
- GitHub Pages 是静态托管；如果用它承载前端，必须另有真实部署的联机服务。最终服务不能依赖我电脑持续开机。
- 面向中国大陆校园网和移动网络使用，字体、脚本、图片尽量随项目提供。没有对应网络的实测条件时，如实标为待实测。
- 正式交付地址应长期可用，不能用 localhost、局域网地址、临时开发隧道或短期预览冒充。
- 需要新登录、账号授权或新增付费资源时，先完成可运行代码、验证和部署配置，再集中说明剩余的最小操作及费用；不要索要粘贴到聊天中的密码或密钥。

## 八、验收要求

测试对应具体风险和规则，保留可复查结果：
1. 2、3、4、5、6、7、8 人都能建房、加入、选秀并开赛；至少实际完成 2 人、6 人和 8 人的全局测试。
2. 用独立 BrowserContext 模拟不同玩家，至少验证 8 个独立身份同时在同一房间。共享同一身份的多个标签页不能充当多玩家验收。
3. 覆盖复制链接、准备与开局、暗选隔离、本人和非本人回合、其他玩家回合中的技能选择、满员、非法动作、重复点击及同时提交。
4. 覆盖刷新、短暂断网、重连失败后的全量同步、手机切后台恢复、房主离线、服务器重启恢复。
5. 每个角色至少有一个有明确预期的技能用例，复杂角色增加组合测试；用例引用对应规则来源。
6. 优先覆盖 Romantic/Suckerfish、Scoocher/Suckerfish、Huge Baby、重掷与掷骰触发、Genius/Skipper、Egg/Twin/Copycat，以及赛道效果、同时移动、出局与终局的交互。各组合预期必须先从现行规则确认。
7. 验证各场计分、四场后总分、角色使用限制、终局立即结束的边界和原房间再来一局。
8. 检查桌面和窄屏手机上的赛道、8 人同格、长中文技能、弹窗与关键操作按钮；用实际截图修正布局。
9. 对正式部署网址再次进行真实多客户端联机验证。记录执行环境、通过项目和确实未能完成的项目，不编造测试结果。

## 九、执行方式与最终回复

先用简短计划说明已确认版本、规则缺口、技术路线与部署候选，然后直接开始实施。可将规则研究、规则引擎、界面美术和联机测试分给不同代理并行处理，先约定数据结构和接口，避免互相覆盖修改。

按“研究与规格 → 打通真实联机 → 完整规则和角色 → 美术完善 → 测试与部署”推进，阶段完成后继续下一阶段。维护简短进度与未解决事项，恢复工作时读取后继续。

最终回复至少提供：
1. GitHub 仓库链接。
2. 正式游戏网址和创建、分享房间的方法。
3. 已实现玩法、36 角色覆盖情况和采用的规则版本。
4. 7～8 人扩展相对官方模式的具体差异。
5. 联机与规则测试结果、部署方式、费用或休眠限制。
6. 确实仍然存在的限制；若部署受授权或资源阻塞，明确区分已完成部分与尚未上线部分。
